# Release Management Platform — Stage 1 Architecture

## 1. Architectural style

The solution uses a pragmatic Clean Architecture split with ASP.NET Core MVC as
the composition root. PostgreSQL is the system of record. Azure DevOps is an
eventually consistent integration and never owns the release workflow.

Dependency direction:

```text
Web -> Application <- Infrastructure
          |
          v
        Domain

Infrastructure -> Domain
```

- `Domain` contains entities, enums, value objects, domain events, exceptions,
  and rules. It has no dependency on EF Core, Identity, MVC, or integrations.
- `Application` contains use cases, ports, DTOs, validators, authorization
  checks, and workflow orchestration. It depends only on `Domain`.
- `Infrastructure` implements persistence, Identity, Azure DevOps, file
  storage, notifications, jobs, and logging ports.
- `Web` contains controllers, view models, Razor views, filters, middleware,
  and dependency injection registration. Controllers remain thin.

The Application layer may use `IApplicationDbContext`; a generic repository is
not introduced. Every command that accesses a release performs resource-level
authorization to prevent IDOR, independently from controller policies.

## 3. Core aggregate and relationships

`Release` is the aggregate root. Changes to workflow state are made only
through the workflow service and persisted atomically with status history,
audit data, responsibility, notifications, and outbox messages.

Main relationships:

- `Product` has many `Service` records.
- `Release` belongs to a `Product` and an `Environment`.
- `Release` has many `ReleaseService`, `ReleaseWorkItem`,
  `ReleaseApproval`, `ReleaseComment`, `ReleaseAttachment`,
  `ReleaseStatusHistory`, and `DeploymentRecord` records.
- `ApplicationUser` has roles and product access.
- `ReleaseApproval` can be assigned to a user or role.
- `AzureDevOpsMapping` stores external synchronization state.
- `Notification` targets a user and may reference a release.
- `AuditLog` is append-only and retains actor and correlation information.
- Outbox messages record integration work in the same database transaction as
  the business operation.

History, approvals, deployment records, and audit logs do not use cascade
delete. Reference data uses `IsActive` soft deletion. Release rows use an
optimistic concurrency token. Dates are stored in UTC.

Release numbers use a PostgreSQL sequence and the format
`REL-{year}-{sequence:000000}`. The number is never generated by reading the
latest row.

## 4. Workflow

The workflow is an explicit transition graph, not a freely editable status
field. Every transition checks the current state, actor role, release access,
required fields, and prerequisite approvals.

Primary path:

```text
Draft
  -> Submitted
  -> ReleaseManagerReview
  -> PentestReview
  -> InfoSecReview
  -> BusinessApproval
  -> Approved
  -> ReadyForRelease
  -> DeploymentInProgress
  -> Deployed
  -> Closed
```

Revision and recovery paths:

- `ReleaseManagerReview -> ReturnedForRevision -> Submitted`
- `PentestReview -> PentestChangesRequired -> PentestReview`
- `InfoSecReview -> InfoSecChangesRequired -> InfoSecReview`
- `BusinessApproval -> BusinessChangesRequired -> BusinessApproval`
- `DeploymentInProgress -> DeploymentFailed`
- `DeploymentFailed -> DeploymentInProgress` for an authorized retry
- `DeploymentFailed -> RollbackInProgress -> RolledBack`
- Active non-terminal states may transition to `Rejected` or `Cancelled` only
  for explicitly authorized roles and with a required reason.

`Closed`, `Rejected`, `Cancelled`, and `RolledBack` are terminal in the first
implementation. Reopening requires a future, separately audited use case.

Each successful transition:

1. validates authorization and business preconditions;
2. updates status and current responsibility;
3. appends status history and audit records;
4. creates deduplicated notifications;
5. writes an outbox message for Azure DevOps synchronization;
6. commits all database changes in one transaction.

## 5. Authorization

Authentication starts with ASP.NET Core Identity and is isolated behind
`ICurrentUserService`, allowing migration to OpenID Connect/Entra ID.

Policies:

- `CanCreateRelease`
- `CanReviewRelease`
- `CanPerformPentest`
- `CanPerformInfoSecReview`
- `CanApproveBusiness`
- `CanDeployRelease`
- `CanManageSystem`
- `CanViewAuditLogs`

Policies protect endpoints; Application authorization verifies access to each
specific release and product. UI visibility is never treated as authorization.

## 8. Persistence and integrations

EF Core configurations use one `IEntityTypeConfiguration<T>` per entity with
explicit lengths, indexes, conversions, foreign keys, and delete behavior.
PostgreSQL migrations live in Infrastructure.

Azure DevOps calls are made only by Infrastructure through `HttpClientFactory`.
Submission succeeds even if Azure DevOps is unavailable: a unique outbox
message is retried by an idempotent background job. The PAT is loaded only from
secret storage or environment variables.

Attachments are stored outside PostgreSQL through `IFileStorageService`.
`LocalFileStorage` is the first adapter; Blob/MinIO can replace it without
changing application use cases.

Hangfire with PostgreSQL storage is the initial job runner. Jobs cover outbox
delivery, email, approval reminders, daily reports, and temporary-file cleanup.

## 9. NuGet package plan

Packages are introduced in the stage where they are first used and centrally
versioned to avoid unused dependencies in inner layers.

- Application: `FluentValidation`,
  `Microsoft.EntityFrameworkCore` abstractions only if required by

- Infrastructure: `Microsoft.EntityFrameworkCore`,
  `Microsoft.EntityFrameworkCore.Design`, `Npgsql.EntityFrameworkCore.PostgreSQL`,

  `Serilog.Sinks.Console`, `Serilog.Sinks.File`,
  `Microsoft.Extensions.Http.Resilience`.

  `Testcontainers.PostgreSql`, `Respawn`, `xunit`, `FluentAssertions`.

Package versions will be selected from stable releases compatible with
`.NET 10` when added. Preview packages are not allowed.

## 10. Cross-cutting requirements

- Structured Serilog events carry a correlation ID.
- Audit records never contain passwords, tokens, PAT values, or sensitive file
  contents.
- Production uses HTTPS, HSTS, secure cookies, security headers, global
  exception handling, and no stack traces.
- Uploads validate size, sanitized file name, extension, MIME type, and content
  signature.
- Sensitive endpoints use rate limiting.
- `/health/live` checks the process only.
- `/health/ready` checks PostgreSQL and required local storage; Azure DevOps
  degradation is reported without making liveness fail.
- Tests cover transition rules, validation, resource authorization,
  concurrency, idempotency, and the full release lifecycle.

## 11. Stage boundaries

Stage 1 establishes the compilable solution and records architectural
decisions. Domain behavior starts in Stage 2. Infrastructure, UI, and
integration packages are intentionally not implemented early so that each
subsequent stage remains reviewable and continuously compilable.
